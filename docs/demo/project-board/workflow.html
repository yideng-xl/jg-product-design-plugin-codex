SKILL WORKFLOW / 方法与流程

需求如何走到原型定稿

产品经理确认业务判断，AI 整理规则、制作原型并核对修改。每一步都有可检查的产出。

体验 Demo
工作方式

先说清规则，再用页面验证，评审后回写。

这套流程由 requirements2prd、prd2prototype 和 proto-check 配合完成。界面、说明和文档使用同一套产品规则，修改时一起核对。

01 判断范围→02 梳理需求→03 制作原型→04 检查评审→05 修改复查→06 回写定稿

发现规则缺口，返回需求讨论；发现页面问题，返回原型修改。产品经理确认评审结论后，才进入定稿。

01 · 先判断要改多大

requirements2prd
独立模块 / 新产品

先看用户、现状、法规、同类工具和自身条件，再确定目标、本轮范围和交付安排。讨论节省什么成本、改善什么结果、满足什么约束。

具体功能 / 页面修改

直接明确谁使用、何时触发、怎么操作、修改边界、已有数据与验收条件。按需要展开，避免重复讨论已经明确的事实。

进入下一阶段的条件

产品经理已确认本次对象、目标和范围。影响设计的事实缺失时，先提出具体问题；示例参数不能当作真实业务结论。

02 · 把需求变成可执行规则

requirements2prd
A

5W 拆解

What、Why、Who、How、When：做什么、为什么、谁使用、怎么使用、何时触发。分别记录客户目标、用户操作和产品方案。

B

对象与状态建模

先区分持续存在的业务对象和一次操作的记录，再定义状态、迁移条件、可做动作与权限。逾期等标签单独表达。

C

视图与 MVP 范围

每个视图回答一个明确问题。用 PDCA 检查规划、执行、检查和改进动作，选择本轮必要内容，写清范围边界。

D

按需探索方案

大模块可用 HMW 重述问题、反向法找失败条件。设计分岔时比较方案代价；关键假设缺少证据时先验证。工具按问题选用。

产出与确认：需求范围、对象关系、状态规则、字段约束、权限、异常和验收标准。影响实现的问题由产品经理确认后写入 PRD。

03 · 用原型把规则讲清楚

prd2prototype
A

先主线，再下钻

抽取关键页面，明确列表、详情、弹窗和返回关系。每个按钮有具体结果，筛选、空态、禁用原因与失败反馈可以体验。

B

复用组件与主题

按产品选择独立组件包，统一按钮、表单、表格、弹窗、术语和布局。此公开样例使用通用项目内容，展示浅色与深色两套主题。

C

说明跟随页面

局部规则绑定控件，点击说明可定位；全局字段和跨页规则放在页底。用户操作文案与评审说明分开呈现。

D

保存人工修改

说明有独立覆盖层，本地编辑器支持修改并保存。迭代时先读已有修改，再调整页面。公网静态预览保留只读说明。

产出与确认：可交互 HTML、共享组件、页面导航和需求说明。主路径与关键异常可演示，页面与规则一致后提交评审。

04 · 自查后再评审

proto-check

按本轮新增或修改的页面与规则检查。核对字段、日期边界、状态、权限、异常、返回路径和跨页术语；实际打开页面验证遮挡、弹窗与交互。

检查结果

区分符合、不符合、部分符合、不适用和需人工确认。问题指向具体页面、控件与规则，给出可执行的整改要求。

安全边界

涉及敏感操作时，在需求阶段确认权限、校验、确认、失败处置和记录要求。原型检查这些规则是否表达；服务端防护由技术与测试验证。

评审决策

产品经理确认取舍与修改范围。缺少证据的检查项保留待核验状态，不能把原型可点击当作生产系统验收通过。

05 · 按反馈修改，并检查受影响页面

prd2prototype + proto-check
反馈类型处理方式复查内容
列宽、配色、间距按已明确反馈调整代表页面、主题与小屏布局
字段名、文案、术语统一名称，查找所有引用列表、详情、表单和说明一致
状态、权限、操作规则已确认规则直接实现；新决策先确认主路径、禁止条件、异常和上下游结果
对象模型、视图或范围变化先确定影响范围，再改页面和需求导航入口、数据关系、规则与验收条件

保留可回退版本：修改前保存基线，每项确认修改验证后独立提交。保留用户的手工说明，复查上次问题及本次连带影响。

用这个 Demo 看一次规则修改

虚构示例 · 不是评审记录

假设反馈是：“任务提交验收后，必须逐项核对，才能标为完成。”

  1. 先确认：谁能验收？哪些项目必须核对？不通过时退回哪一个状态？
  2. 写成规则：本样例管理员在“待验收”状态核对全部验收项后完成；退回必须填写原因，状态回到“进行中”。
  3. 落实页面：任务详情展示验收清单；条件不满足时禁用完成按钮并显示原因。退回弹窗校验原因，操作记录保留结果。
  4. 检查影响：核对任务状态、项目进度、看板统计和访客只读行为。修改规则时同步更新 R-06 及验收场景。
  5. 回写材料：评审确认后，将字段与行为写入细则，将业务规则写入 PRD，再核对原型与文档。

06 · 评审通过后回写、定稿

prd2prototype
  1. 逐页更新 PRD 细则：按页面和功能记录字段、状态、操作、异常、边界、权限与数据来源。
  2. 回写 PRD：同步确认后的范围、规则和产品决策。纯视觉样式留在原型或设计稿。
  3. 核对三份材料：细则、PRD 和原型使用相同术语、状态与行为；有冲突先确认口径。
  4. 交付研发：材料一致后生成研发对接版需求说明书，明确本轮功能、范围边界与验收标准。格式、版本和状态遵从当前交付约定。

定稿条件：产品经理确认本轮结论；主路径与关键异常已检查；影响实现的规则明确；文档与原型一致。发布页面本身不代表评审已通过。
