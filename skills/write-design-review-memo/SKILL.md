# 设计评审备忘录

把会议事实压缩成可上传、可跟踪的备忘录。只记录有依据的基本信息、共识、待办、结论和必要复盘。

## 读取依据

1. 先读项目指引和用户提供的逐字稿、会议记录、PRD、原型。
2. 如果工作区存在 `90-dailyWork/00-规范/设计评审备忘录关键字.docx`，完整读取。
3. 用户在当前对话中的新要求优先于历史模板。
4. 不确定的人员、时间、结论写「待确认」，不得补写。

用户指定的逐字稿或会议记录是会议结论和待办的唯一事实源。PRD、原型只用于核对术语和理解上下文，不得把其中的参数、状态、规则或责任人写成会议共识。

## 整理流程

### 1. 提取事实

在起草前分开记录：

- 基本信息：产品、需求、时间、参会人员、材料链接；
- 前置条件：会前已经完成的确认和准备；
- 会议决策：明确采纳、保留、删除、待评估的事项；
- 待办：会议明确的事项、责任人、时间；
- 评审结论：通过，或待二轮评审；
- 复盘证据：会议暴露的问题及可落到管理体系的改进项。

每项结论和待办在内部保留对应原话、发言人和上下文。语音转写不清时标「待确认」或不写。

待办只收录两类事项：

- 会议主持人明确分配了事项；
- 当事人明确承诺了事项。

“建议”“需要”“可以补”“研发评估”等表达本身不是已分配待办。不要根据汇报人、模块负责人或角色替会议分配任务。事项已确认但责任人或时间未定时，写「待确认」；不要把「下周」「明天上午」改成自行推算的日期。

不要为了填满责任人、时间或二次评审日期而新增“确认责任人”“确认日期”等待办。「待确认」只补在会议已经明确要做的事项上。

### 2. 按固定结构成稿

```text
一、基本信息
二、会议共识/待办事项
三、评审结论
四、复盘总结（按条件输出）
```

基本信息包括参与人员、沟通时间、评审产品和需求，可附在线文档链接。前置条件只写会前已经完成的关键动作。

会议共识只保留会后仍需执行或影响方案的结论。删掉讨论过程、重复解释和未形成结论的发散内容。

### 3. 待办使用上传格式

每条待办只占一行，固定为：

```text
事 --人 --时间
```

示例：

```text
补充数据流图和字段样例 --责任人待确认 --二次评审前
```

不用表格，不拆成三行，不写成「某人：事项。时间：某日」。

### 4. 写评审结论

使用与会议一致的结论：

- `评审通过，进入开发阶段。` 后续写明需求确认和技术设计评审；
- `完成一轮评审，待二轮评审。` 写明二轮只评什么。

一个会议包含多个评审对象时，先分别写结论，再给整体结论。只要关键对象待二轮评审，整体不得写完整通过。

整体待二轮评审时，结论首句固定写 `完成一轮评审，待二轮评审。`。会议中的“不通过”作为原因说明，不替换该标准结论。

### 5. 判断是否复盘

- 功能调整或易用性需求且评审通过：可不写复盘；
- 逻辑复杂、评审未通过、带条件通过或待二轮评审：必须写复盘。

复盘只写做得好的地方、存在的问题、改进措施。发现可通过评审准入、模板、检查项或流程解决的问题时，给管理体系专员一条具体建议。

管理体系建议不是会议待办。除非会议明确分配，否则用普通文字写建议，不追加 `--人 --时间`。

## 文件与文字要求

- 文件名：`YYYY-MM-DD-产品或项目名（版本号）-设计评审-Codex.md`；
- 默认放在对应产品迭代目录；
- 篇幅从会议内容中长出，能短就短；
- 正式内容不写公司名和用户名，不用营销词；
- 草稿保留 `-Codex`，用户确认定稿后再去掉。

## 交付前检查

- 基本信息、前置条件、共识、待办、结论是否有来源；
- 每条待办是否严格为一行 `事 --人 --时间`；
- 是否误用表格，或擅自补了责任人、时间、参会人员；
- 每项共识和待办是否能在指定会议记录中找到明确原话；
- 是否把 PRD、原型中的内容误写成会议结论；
- 是否为了补齐字段新增了会议没有提出的“确认责任人”或“确认日期”待办；
- 复杂或待二轮评审时是否有复盘；
- 整体结论是否与各评审对象结论一致；
- 是否保留了待确认项。

## 常见错误

- 把逐字稿改写成长篇会议过程；
- 为了让材料完整，给未分配事项补责任人；
- 把“建议补充”或“需要研发评估”直接写成指定人员待办；
- 从 PRD、原型补入会议没有确认的参数和状态；
- 把相对时间改成会议未确认的具体日期；
- 把管理体系建议写成已分配待办；
- 待办使用表格，导致上传后难以编辑；
- 关键流程尚未讲清，却写「评审通过」；
- 复盘只写业务问题，没有提出可落到管理体系的检查项。
