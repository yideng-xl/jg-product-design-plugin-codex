# 产品部周例会标准

本标准由《产品部周例会-会议制度》、人工定稿纪要及 2026 年 10 月 19 日会议定稿及后续确认的修改规则共同提炼。会议制度决定议程、主持要求和会后要求；人工定稿决定实际成稿的栏目、排版和压缩方式。

## 一、会议议程与时间

1. 上周闭环确认，2 分钟。会前逐项确认状态；会上只同步结果并追问未完成项。
2. 关键信息分享，3 分钟。部门负责人或业务专家按需分享公司、客户和协同部门的关键信息。
3. 重点工作汇报，18 分钟。按产品方向汇报，成员发言后集中追问。
4. 管理体系建设与执行，6 分钟。汇报体系成果、执行抽查和工作计划，不展开详细过程。
5. 人员培养及团队建设，10 分钟。安排周报复盘、方法讨论和能力进展。
6. 本周闭环确认，1 分钟。主持人逐项确认任务、责任人和完成时间。

管理体系和人员培养两部分不能连续两周没有实质内容。没有重大更新时，相关负责人仍需说明在办事项的状态。

## 二、主持要求

- 汇报先给核心结论。成员发言按“成果、风险、决策”组织，控制在 1.5 分钟内。
- 同一产品方向全部成员讲完后，再集中追问依赖关系、影响和需支持事项，控制在 2 分钟内。
- 部门负责人最后补充，避免先给答案影响成员判断。
- 延期事项要追问原因、已经尝试的处理方式、需要的支持和新的完成时间。
- 以下内容应当场收住：只有动作没有成果结论；只与少数人相关的技术细节；明显超时。
- 远程会议按团队约定开启摄像头。发言结束明确交回主持人。

这些要求由主持人执行。会前稿默认也不预写主持核对、备选追问或口头串词，只保留现场补充空位。正式纪要只记录结果，不抄入时长、主持提示或会场规则。

## 三、正式纪要固定结构

正文固定为 6 个章节：

1. `一、上周闭环项`
2. `二、关键信息分享`
3. `三、重点工作汇报`
4. `四、管理体系建设与执行`
5. `五、人员培养及团队建设`
6. `六、本周闭环`

MD 是起草和修改载体，可使用章节和产品方向的 Markdown 标题；最终 TXT 去除 Markdown 标记。不加总标题、日期副标题、基本信息、前言、主持提示、表格、引用块或分隔线。保留用户当前排版。

## 四、各章节写法

### 1. 上周闭环项

会前每项写任务、结论和现场留空：

```text
1、<上周任务>。--<责任人>，<原定时间>
会前情况：<已完成/部分完成/未完成；结论、剩余缺口、新时间>
现场补充：
```

结果直接写结论、剩余缺口和下一时间点，不写“周报记录”“材料显示”等取材过程。涉及具体产品版本时保留版本号和功能名，检查清单和过程记录留在原材料中。会前未取得结果时留空或标明待确认，不能补成已完成；用户已确认的结论优先。

### 2. 关键信息分享

只收会中明确分享、且会影响部门判断或行动的信息。没有内容时写 `无。`；会前主持稿可留空。

### 3. 重点工作汇报

按 `【网管】`、`【集管】`、`【网安】` 等实际产品方向分组。人员与方向以最近正式纪要和本周材料为准，不把名单固化在 Skill 中。

会前可使用以下栏目；会后仅保留有内容的栏目：

```text
1、<姓名>
成果：<已完成产物、已确认结论或已发生结果>
风险和决策：<有实质内容时填写，无则省略整行>
本周重点：<会上同步或用户确认的安排>
```

无实质风险或决策时省略整行，不填“无”。缺少该成员周报或遗漏工作时，先查同期设计评审备忘录等材料，补入能确认的成果；仍无依据的内容留空。会前可从周报提取计划；会后“成果”“本周重点”仅收会上实际同步或用户明确确认的内容，删除仅来自周报的事项，写短句并保留产品版本号。

会前在同一方向所有成员之后保留“现场追问及结论”空位。会后按实际内容填写，例如：

```text
追问及建议：
1、<会议形成的判断、要求或建议>
```

没有内容时写 `无。`。跨产品方向的共同要求确实无法归入单一方向时，可以在相关方向之间或之后增加 `网管、集管综合建议`，只写 1 次。

### 4. 管理体系建设与执行

标准子项为产品管理、业务专家、产品设计与 AI 应用。按本周实际材料选择详细写法或合并写法：

```text
1、产品管理：
2、业务专家：
3、产品设计与 AI 应用：
```

3 个方向均无更新且会上未提出执行要求时，可以压缩为 1 行。有明确要求时，写清用什么案例解决什么执行问题、结果如何传递和跟踪，不压成“执行现有体系”。同一成果不要在成员产品成果中重复。

### 5. 人员培养及团队建设

保留周报复盘、团队共识和能力进展；自 2026.10.19 起增加轮流调研分享：

- 从[待调研清单](https://365.kdocs.cn/l/ckZtfQQ8ix80)中，每次选 1 项已有结论的内容分享结果，再选 1 项尚无结论的内容作为后续调研方向，明确主题名称即可，有结论后及时同步。
- 网管、集管分开分享，按周轮流。以 2026.10.19 集管、2026.10.26 网管为起点；后续按周推算，最新明确安排优先，遇停会等例外未明确如何顺延时不擅自调整轮次。
- 业务专家为主、产品经理配合，由双方协商分享人。集管由赵雪岩、许磊协商，网管由许江辉、陈文浩协商；人员有新安排时按最新确认执行。
- 会前写明当周方向，保留“已得出结论的主题”“分享结果”“后续调研主题”“分享及讨论补充”空位。只有来源已明确或用户提供的主题、结论才填写，不替成员选择或编造。
- 用户已精简的稿件保留其结构，不反复补回整段制度说明。

### 6. 本周闭环

每项固定包含 3 个要素：任务、责任人、完成时间。

```text
1、<任务>。--<责任人>，<完成时间>
```

待办只收会议明确分配、责任人明确承诺或用户确认的事项。保留实际交付标准：如“收集数据并与负责人分析出结论”，不能缩成“形成安排或判断”。建议、愿望和无人承接的讨论不写成待办。

## 五、内容取舍

| 内容 | 写入标准 |
| --- | --- |
| 成果 | 已完成的产物、已确认的结论、已发生的业务结果。压缩成短句，同一人的多个成果用分号分隔。 |
| 风险和决策 | 影响目标、范围、资源、版本、技术路线、发布安排或客户承诺的重大变化，以及需要负责人拍板的事项。 |
| 普通延期 | 只改日期、常规等待、一般进度偏差通常不写入风险和决策。会议专门讨论并形成处理结论时再写。 |
| 追问及建议 | 会中形成、会后仍会影响工作的判断、要求和建议。不能从周报自行推导。 |
| 闭环结果 | 结论、剩余缺口、下一时间点。过程材料不搬入纪要。 |
| 未定讨论 | 写清未定点和下一步。缺少收口时不能写成已确认结论。 |

## 六、语言与发布要求

- 会议纪要是结论记录，不按发言顺序复述。
- 先写结果，再补必要原因和边界。句子保持短。
- 关联内容按主题合并，避免重复解释。完整待办集中在第六节；前文保留必要的判断、责任边界、执行要求，与末尾行动清单可以有简短呼应，不要求同一事项只能出现一次。
- 产品成果和计划保留具体版本号及对应功能名称，不为简写删掉版本。版本不明确时不猜填。
- “本周、下周、上周、本周上半周/下半周”等不补括号日期，也不自行转换为日期范围。明确周几才补 `月.日`，如“本周二（10.20）”“下周一（10.26）”；“下周公司周例会”不因已知惯例自行加日期。已有明确日期用 `10.23`。章节标题和栏目名不加日期；“11 月中旬”等模糊时点不编造具体日期。
- 每次编辑前重新读取当前 MD，仅修改本次要求涉及的内容，核对差异，保留人工结论、顺序、删减和留空。
- 起草和修改用 MD，用户确认后从最新 MD 生成最终 TXT，去掉草稿后缀和 Markdown 标记，并核对正文一致。
- 数字用阿拉伯数字，中英文之间留空格。
- 正式内容不出现公司名或工具用户名。人员姓名只用于成员汇报、责任人或确有必要的发言事实。
- 会后 24 小时内发布正式纪要。发布前检查本周闭环的任务、责任人和完成时间。

## 七、定稿体现的写法

以下是可复用的编辑规则，不把某次会议的业务决定固化为以后每周的要求：

- 个人汇报简短；补充和追问保留会上明确的管理判断、责任边界、执行方式和结果去向。不要为了压缩删除关键要求。
- 上周任务结果与会中要求分开，后者可集中放在该节“追问及建议”。正式稿压缩多余空行，不保留空风险栏目。
- 同一话题区分已有问题怎么处理、新问题怎么发现和记录；只有会上提出时才分成“存量/增量”，不强制套用。
- 写清谁是第一负责人、谁配合、数据收集频率、谁参与分析、产物发到哪里。准确保留定稿里的量化要求，不把“每月至少一次”改成更宽泛的“定期”。具体频率来自当次会议或用户确认。
- 技术资产要求写清对象及用途，如安全条款对应产品环节和方案约束、数据采集的方法工具、系统接口的输入输出字段；不要只写“积累经验”。
- 判断和状态以最新定稿为准。“待定义”不改成“待反馈验证”，“客户改变方案”不等于“我方话术已验证有效”；未定建议不写成最终方案。
- 调研编号和主题名称有来源时一起保留；未知名称不猜填，用户补充名称后更新。具体主题、客户策略和任务不作为固定模板内容。
