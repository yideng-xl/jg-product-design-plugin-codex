# 日常迭代安全自查表

> 用途:检查本次新增或修改内容是否带来新的安全攻击面,以及产品规则是否表达完整。
>
> 边界:本表只查本次迭代命中的场景。登录、账号口令、会话、系统级角色、全局审计字段、TLS/SSL、端口和中间件加固等框架能力,本次未改动时不重复检查;本次有改动时再纳入。

## 判定方式

先扫描 14 个触发场景,再检查命中项。未命中的项目记“➖ 不适用”,并写明理由。

每个命中项分两层记录:

1. **产品规则**:检查页面、proto-note、字段规格表或需求说明是否写清用户能做什么、边界是什么、失败后如何处理。结论使用 ✅ 已表达 / ❌ 缺失 / ⚠️ 不完整 / ➖ 不适用 / ❓ 需人工确认。
2. **运行防护**:服务端校验、权限强制、注入防护、加密、组件漏洞等无法从静态 HTML 证明的内容,统一记“❓ 需技术评审/测试验证”。不得因界面有限制、说明写了规则或前端做了校验就判为安全通过。

产品规则的 ❌/⚠️ 进入原型整改要求;运行防护单独进入技术/测试承接清单,不要求原型用前端代码模拟安全能力。

### 前后端 check 共性要求

- 凡存在页面输入、文件选择、地址填写、操作提交或权限入口,必须明确**前端和后端都执行 check**。前端用于即时提示,后端必须独立执行同一基线规则,且可以更严格;只有前端 check 不能通过。
- 没有前端页面的外部接口、回调、消息接入和供应链检查,按实际入口标明网关、接入层、服务端、构建或供应链流程,不生造前端 check。
- 原型说明或需求必须逐条列出 check 规则,至少写清:**检查对象、允许/禁止条件、前端执行点、后端执行点、失败提示或处置**。只写“安全校验”“合法性校验”“过滤特殊字符”“按规范处理”均视为未写清。
- 同一条规则在前后端的口径不一致时,说明差异和后端最终判定口径。安全报告必须把规则清单及执行位置原样列出,不能只写“已 check”。

## 自查项

| 编号 | 触发场景 | 原型或说明中应表达,含需逐条列出的 check 规则 | check 执行位置 | 技术评审/测试承接 |
|---|---|---|---|---|
| S-01 | 允许输入或执行命令、脚本、SSH、终端操作 | 写清输入方式(固定模板+参数或自由输入)、允许的命令、选项及参数类型/长度/范围、禁止的连接符/重定向符/命令替换/多行输入、目标对象和影响范围、执行权限、再鉴别/审批/确认、超时与并发限制、执行结果和部分失败处理、审计留痕。必须逐条列出 check 规则;自由输入作为高风险设计单列说明 | **前端+后端**。前端按规则即时提示或拦截;后端按同一规则清单独立校验并作最终判定 | 验证前后端 check 与规则清单一致;后端是否避免把用户输入拼接给 Shell;越权、绕过和 Shell 注入测试 |
| S-02 | 允许编辑或执行 SQL、DSL、表达式、模板、规则 | 逐条列出允许的语法、函数、变量、访问对象、字符/长度、执行或预览范围、资源和结果上限、失败处置;明确禁止的危险语法。不得只给一个无限制自由输入框 | **前端+后端**。前端做语法和范围提示;后端独立解析、校验和限制实际执行范围 | 验证前后端 check 一致、解析执行隔离、危险语法限制;SQL/表达式/模板注入及资源耗尽测试 |
| S-03 | 可配置接口、连接及请求参数控件 | 页面允许用户配置外部接口、连接参数、请求头、Query、Body、认证参数、自定义键值或字段映射时,逐条列出可配置项、类型、长度、范围、字符集、是否必填、允许/禁止内容、字段关系和失败处置。普通名称、备注、查询条件等仍由产品表单自查项检查,不重复命中本项 | **有配置页面时前端+后端**;仅接口入参时由网关/接入层+服务端校验。后端均需独立执行 | 验证后端 check 未依赖前端;边界值、超长内容、参数篡改和注入测试。涉及地址同时检查 S-07,对外开放接口检查 S-13,凭据/密钥检查 S-09 |
| S-04 | 富文本、HTML、Markdown、留言、搜索内容等会被再次展示 | 明确是否允许 HTML;允许时逐条列出标签、属性、协议、链接、图片和长度白名单;列出内容在页面、通知、导出或日志中的回显位置及各位置的处理规则 | **前端+后端+输出端**。前端提示输入边界;后端校验/净化;每个输出位置按上下文转义或净化 | 验证各执行点与白名单一致;存储型、反射型和 DOM 型 XSS 测试 |
| S-05 | 文件上传、导入、压缩包解析 | 逐条列出允许的扩展名、真实文件类型、大小、数量、文件名、内容/模板版本,重名和重复数据规则,解析失败与部分成功处置;压缩包列出层级、文件范围和解压后总大小限制 | **前端+后端**。前端做选择和大小提示;后端重新校验文件类型、内容、数量及解压规则 | 验证后端不信任前端文件信息、采用不可执行存储;恶意文件、压缩炸弹、路径穿越和覆盖测试 |
| S-06 | 文件下载、目录/路径选择、数据导出 | 逐条列出可下载对象、允许路径/对象标识、数据范围、字段、时间/数量上限、脱敏、审批/确认、结果与留痕规则。下载文件名固定为 `页面名称_YYYYMMDD_HHmmss.扩展名`,页面名称取当前页面标题,例如 `告警查询_20260825_143025.xlsx` | **前端+后端**。前端限制可选范围并核对最终下载文件名;后端独立校验对象、路径、数据和字段权限,并按统一规则生成文件名 | 验证前后端范围一致、下载文件名符合规范;任意文件读取、路径穿越、越权下载和批量拖取测试 |

## 报告记录要求

- 证据必须指到具体页面、控件、proto-note、字段规格表或需求段落。
- 同一功能命中多个场景时分别检查。例如“上传脚本并远程执行”至少命中 S-01、S-05、S-08、S-10,不能只记一条。
- 产品规则已经写清但仍需运行验证时,可以同时记录“产品规则 ✅”和“技术/测试 ❓”。两者不互相替代。
- 命中需 check 的条目时,报告必须逐条抄录 check 规则及其执行位置。未列规则、只标“前后端已校验”时,产品规则不能判 ✅。
- 发现本次迭代改动了框架能力时,在报告中写明“框架项变更”,转入对应专项评审,不在本表临时扩写通用框架清单。
