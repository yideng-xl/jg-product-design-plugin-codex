# 原型自查 → 整改要求

> 定位:`prd2prototype` 产出原型之后、产品评审之前的质检环节。依据三套固化标准逐条检查,产出**自查报告**(给人看结论)和**整改要求**(直接粘贴给原型生成会话执行整改)。

## 核心心法:判定对象分三类

静态 HTML 原型**不是可运行系统**,逐条判定前先分清这条标准考的是什么:

1. **界面呈现**:界面上直接看得出(必填 * 号、按钮颜色、Tag 样式、分页组件……)→ 直接对源码/渲染结果判。
2. **规则表达**:实现层/运行时标准(防抖、响应 200ms、自动保存、判重逻辑……)→ 原型不要求真实现,判定口径 = **原型说明(proto-note)/字段规格表里写没写清这条规则**。写清了 = 符合;没写 = 不符合(整改方式是补说明,不是写 JS)。
3. **安全运行防护**:服务端校验、权限强制、注入防护、加密、防重放、组件漏洞等 → 静态原型只能检查产品规则是否写清,实际防护统一进入**技术评审/测试验证**,不得从前端限制或说明文字推断安全通过。

产品/UI 标准的判定手段已标注在「原型检查口径」列的标签里:**【源码】/【渲染】/【说明】/【人工】**。纯运行时/生产环境条目(响应时长、防抖等)已从 UI asset 删除、不参与 UI 自查。安全 asset 保留运行防护承接项,但不计入原型通过率。

同一次自查必须使用**同一 skill 目录**中的 `SKILL.md` 和 `assets/`,并在 `自查/口径.md` 记录实际来源路径与条目数。工作区存在待维护的源码时,不得改用已安装缓存中的旧版规则,也不得混用两个版本的条目。

## 检查范围先按迭代类型划分

1. **新增页面 / 新增功能**:检查新增范围涉及的全部适用项。
2. **修改既有页面**:只检查本次改动和被改动直接影响的规则。既有页面可用于判断本次改动是否保持一致,但不检查、不记录、不整改与本次迭代无关的存量问题。
3. **新增与修改混合**:新增部分完整检查;修改部分按影响范围检查。

报告只列本次检查范围内的条目。范围外条目不判定、不计数、不写进报告。用户明确要求检查既有页面全量内容时,再扩大范围。

## 判定纪律(铁律)

- **每条结论必须有证据**。判「不符合」要写明:哪个文件、哪个位置、现状是什么;判「符合」也要能说出依据(抽查到哪几处)。禁止没看就批量打勾。
- **判不了就说判不了**。渲染类条目浏览器不可用 → 标「需人工核验」;主观类(人工)条目 → 只描述现象不下结论;纯 PRD 层面条目 → 进「需人工确认」清单。**不强行给结论。**
- **不适用要写理由**(如"本原型无树形控件,Z-树-* 不适用")。
- **结论分五档**:✅ 符合 / ❌ 不符合 / ⚠️ 部分符合 / ➖ 不适用 / ❓ 需人工确认。
- **安全项分两层结论**:产品规则仍按五档判定;运行防护只记“❓ 需技术评审/测试验证”,不得用产品规则结论代替。
- **整改建议给到"怎样算改好"**,不是复述标准原文。

## 流程(五步)

### 第 1 步:盘点与确认范围

- 列出原型目录的页面清单(html 文件),确认 common.css / common.js / index 是否齐全。
- **先做工程预检,再开始产品自查**:扫描全部 HTML 中 CSS、JS、数据文件的 `?v=` 查询值。一个原型交付内出现多个值时,先统一为本轮已使用的最新工程修订号,再进入评分。该查询值只用于破除缓存,不改变页面可见的原型版本,不写入版本变更记录,也不计入产品自查的 ❌/⚠️、整改条数或通过率。无法确认统一值时,单列“工程预检待处理”,仍不得计入产品自查统计。
- 工程预检发现的资源查询值、数据文件头部版本注释等不一致,只作为生成质量问题单列处理。不得临时增造 `Z-版本-*` 检查项,也不得放进产品/UI 通过率。
- 用 `向用户提问并等待明确确认` 确认:本次属于**新增、修改还是混合迭代**?具体改了哪些页面、区块和规则?用户是否明确要求扩大检查范围?
- **先收主观口径**:部分条目判据含主观词(F-03"关键指标"、F-06"高频操作"),开查前问用户一次,答案存原型目录 `自查/口径.md`,复查时复用不再问;用户未给口径的,这些条目只查"有无",不判"对不对"。
- 按本次新增 / 修改内容判断涉及的功能类型(表单/列表/统计……)。新增范围挂全部适用类别;修改范围只挂改动项和直接受影响项。
- 按 `日常迭代安全自查表.md` 扫描 14 个触发场景。只检查本次命中项;登录、账号口令、会话、系统级角色、全局审计字段、TLS/SSL、端口、中间件加固等框架能力,本次未改动时不重复检查。本次改动框架能力时,标记“框架项变更”并转专项评审。

### 第 2 步:静态逐页检查(主体)

- 逐页读本次检查范围内的 HTML 源码,先查「源码」类条目;同时读对应 proto-note / 字段规格表,查「说明」类条目。
- 检查 Z-表单-* / C-04 前先判断是否为新增、编辑、提交业务对象的录入表单。查询/筛选区和仅保存查询条件的个人模板不属于业务录入表单;查询条件允许为空时,Z-表单-01、C-04 记不适用。默认值、默认勾选和查询前置校验不得直接推断为业务必填字段。
- 检查 Z-树-02 时,区分树管理与树选择。可维护或可独立排序的树需写清排序和操作;只用于选择且复用既有资源层级、固定数据源顺序或已给出固定示例顺序的树,无需额外提供人工排序操作,有明确顺序证据即可判符合。
- 检查 Z-接口-01 时先确认本次是否新增或修改系统/模块接口。仅复用既有数据与接口、无接口改动时记不适用;确有新增或改动时,再检查对接流程、字段和修改/删除规则。PRD 已明确写出缺口时可直接判不符合,只有业务事实无法从材料确认时才进「需人工确认」。
- 检查 Z-整体-03 时,业务流程图只对新增或改变多角色、多状态、跨模块流程的需求必查。单页查询/统计且复用既有逻辑,已有清晰的文字操作流程时记不适用;不得仅因没有流程图要求补图。
- 检查 E-03 时,从查询区向列表逐项核对:查询区出现的字段必须有对应列表列。不要反向要求每个列表字段都配置搜索或筛选条件。
- 检查 C-03 前先确认异常是否已有分类和处置规则。规则已确认时检查原因与建议是否齐全;尚不能归类时标记“➖ 不适用(本阶段暂缓检查)”,不进入整改要求,也不让原型补写未经确认的建议。
- 检查 Z-说明-03 时只核对非常用或不直观逻辑。增删改查、普通查询 / 重置、批量删除、弹窗关闭、Tab / 图表切换、普通分页等常规操作未写入清单,直接视为符合,不得要求补齐。
- 检查 Z-列表-06 时,先统计表格实际列数并核对业务是否明确要求自定义列。列数不超过 15 且无特殊要求时,没有入口直接判符合;列数大于 15 或业务明确要求时,再检查自定义列入口及默认展示列、可选列、固定列说明。
- 跨页一致性条目(T 类、Z-整体-08)可横向读取既有页面作为参照,结论只针对本次新增 / 修改内容。参照页里的无关存量问题不写入报告。
- 色值/尺寸类(T-01/T-07/T-12 等):原型若正确引用 common.css 且无页面内硬编码覆盖,默认判符合;发现内联样式硬编码色值/尺寸即重点核对。
- 对命中的 S-* 项,先查页面、proto-note、字段规格表或需求说明是否写清产品规则,再列出技术/测试承接。凡存在页面输入或操作,必须明确前端和后端都执行 check,并逐条列出检查对象、允许/禁止条件、前端执行点、后端执行点、失败提示或处置;只有“安全校验”等概括描述不能判符合。不得因输入框限制、按钮隐藏、前端校验或原型说明已存在,把服务端防护判为符合;也不得要求原型补一段 JS 来假装完成安全防护。

### 第 3 步:渲染抽查(Chrome 可用时)

- 「渲染」类条目(hover、遮挡、F-05 屏内色彩数量、抽屉/弹窗交互)用浏览器打开代表性页面确认,必要时截图留证。
- Chrome 不可用 → 这些条目一律标「需人工核验」,在报告中单列,**不中止流程**。

### 第 4 步:产出四份文件

输出到原型目录下 `自查/` 子目录,文件名带日期与 `-Codex` 后缀(草稿约定):

1. `产品自查报告-YYYYMMDD-Codex.md` —— 依据自查表
2. `UI规范自查报告-YYYYMMDD-Codex.md` —— 依据七大原则量化标准(原型检查版)51 条
3. `安全自查报告-YYYYMMDD-Codex.md` —— 依据日常迭代安全自查表14项,分开记录产品规则结论和技术/测试承接
4. `整改要求-YYYYMMDD-Codex.md` —— 汇总产品、UI 报告及安全报告中产品规则的 ❌/⚠️ 项,可直接粘贴;安全运行防护不混入原型整改

### 第 5 步:与用户对齐整改清单

把不符合项过一遍(用户可剔除/降级),确认后整改要求才算定稿。整改完成后可再跑本 skill **复查模式**:只查上次 ❌/⚠️ 项,输出复查结论。

## 整改要求模板(直接粘贴给原型生成会话)

整改要求的读者是**正在跑 prd2prototype 的另一个会话**,所以:

- **按页面分组**(对方按页改),每条带标准编号、问题现状、整改要求(= 验收口径)。
- **用产品经理口吻的自然语言**写整改要求,不写 CSS 类名/色值等实现指令(对方 skill 自己知道怎么落地);涉及"说明"类问题,整改动作写明是**补 proto-note 业务规则**。
- 开头给足上下文,结尾给完成要求。

```markdown
# <原型名> 自查整改要求(YYYY-MM-DD)

以下是对本原型按《产品设计自查表》《七大易用原则量化标准(总体设计规范V1.1)》和《日常迭代安全自查表》自查后的原型整改要求,共 N 条,按页面分组。请逐条整改;整改遵循 prd2prototype 的既有约定(复用 common.css 组件、说明写在 proto-note、PM 口吻)。技术评审/测试验证项已留在安全自查报告中,不要求原型模拟实现。

## 页面:xxx.html
1. 【T-10】"添加设备"按钮与其他页面的"新增"命名不一致 → 统一改为"新增"。
2. 【C-04】新增弹窗中"设备名称"为必填但无红色 * 标注 → 补必填标识,并确认其余字段必填性。
3. 【Z-表单-05】各字段未说明长度上限 → 在 proto-note 字段规格表补充:无特殊要求的按默认(短文本 50/长文本 300)写明。

## 页面:yyy.html
...

## 跨页面(一致性)
...

## 整改完成要求
- 逐条回报:已改(怎么改的)/ 不改(理由),不要漏条。
- 整改只针对上述条目,不要顺手重构无关内容。
- 全部完成后回复整改清单,我方将做复查。
```

## 与姐妹 skill 的衔接

- 上游:`prd2prototype` 产出原型 → 本 skill 自查 → 整改要求粘贴回原型会话 → 整改后复查 → 通过后进产品评审。
- 评审通过后走 `prd2zentao` 拆研发需求。本 skill 的「需人工确认/PRD 层面」清单可作为 PRD 补全输入(回到 `requirements2prd`/PRD 文档补齐);安全报告中的运行防护清单留给后续技术评审和测试验证承接。

## 踩坑提醒

- **别把"原型没实现 JS 行为"判成不符合**:防抖、自动保存这类是研发实现层,原型只需说明里写清。判错会产生一堆无效整改条目,稀释真问题。
- **别把"原型写了安全说明"判成安全通过**:S-* 项的产品规则与运行防护分开记录。说明写清只能证明产品规则已表达,服务端防护仍需技术评审/测试验证。
- **一致性问题不要拆散到各页面**:同一个命名不统一问题在 5 个页面出现,整改要求里写**一条**(跨页面组),列出涉及页面;拆成 5 条会让整改会话重复劳动。
- **报告别写成论文**:用户明确要求"简单表格:查了什么、哪些没问题、哪些有问题、怎么改"。控制在表格 + 统计行,无总结陈词。
